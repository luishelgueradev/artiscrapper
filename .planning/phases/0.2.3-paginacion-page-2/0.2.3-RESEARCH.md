## 1. Por qué Page 2 (justificación empírica)

El primer nightly del harness (post-recalibración) mostró que **5 de 12 queries saturan el shopping panel cap de Google a 30 pla-units en page 1**:

| Query | Page 1 real_urls |
|---|---:|
| electro-espec (termotanque rheem) | 39 |
| electro-broad (heladera samsung) | 40 |
| ropa-espec (zapatillas nike air max) | 39 |
| pelota-deporte (pelota futbol adidas) | 41 |
| auto-espec (filtro aceite ford focus) | 21 (próximo a cap) |

Las queries más densas comercialmente paran porque Google capa el shopping panel a 30 productos por SERP page — agregar page 2 es la forma estándar de Google para extender el catálogo.

Empíricamente (un quick test manual con `curl https://google.com/search?q=...&start=10`), page 2 sirve un **set mayoritariamente nuevo** de pla-units + organic (NO una repetición de page 1). El dedupe por URL canónica debería colapsar los pocos solapamientos (típicamente top-tier MELI products que Google muestra en ambas pages).

### Patch 2 — New setting `SEARCH_FETCH_PAGES`

```python
# Phase 0.2.3 PAGE2-01: number of SERP pages fetched per query. Each page
# costs one browser context + one fetch_serp call. With pages=2 each
# /search uses 4 contexts total (A page 1, A page 2, B page 1, B page 2),
# so BROWSER_RECYCLE_AFTER=200 fires every 50 /search calls instead of 100.
# Cap at 3 because page 3+ heightens CAPTCHA risk to a level the spike
# never validated.
SEARCH_FETCH_PAGES: int = 2

@field_validator("SEARCH_FETCH_PAGES")
@classmethod
def _validate_search_fetch_pages(cls, v: int) -> int:
    if not 1 <= v <= 3:
        raise ValueError(f"SEARCH_FETCH_PAGES must be in [1, 3], got {v}")
    return v
```

### Patch 3 — `/search` pipeline change

Replace the existing 2-fetch block with an N-page loop:

```python
# ── [2] Google fetch: N pages × 2 (meli/non-meli) in parallel ──
browser = request.app.state.browser
rate_limiter = request.app.state.rate_limit
N = settings.SEARCH_FETCH_PAGES

fetch_specs = []  # list of (page, meli, url) for downstream telemetry
fetch_coros = []
for page in range(1, N + 1):
    for meli in (False, True):
        url = build_serp_url(body.query, meli=meli, page=page)
        fetch_specs.append((page, meli, url))
        fetch_coros.append(fetch_serp(browser, url, rate_limiter))

try:
    results = await asyncio.gather(*fetch_coros)
    request.app.state.browser_uses += len(fetch_coros)
except Exception as exc:
    # All-or-nothing: a single fetch failure aborts the whole /search,
    # matching the prior 2-fetch behavior. Partial-success would
    # require deciding how to mix half-pages, which is out of scope.
    log.warning("google_fetch_failed", error=str(type(exc).__name__))
    return SearchResponse(
        query=body.query, results=[],
        metadata=Metadata(
            elapsed_ms=int((time.time() - t_start) * 1000),
            cache_hit=False, block_detected=False,
        ),
    )

# Track first block found (so consumer sees A consistent block_reason).
# Page 1 HTMLs go to cache (keys html_a / html_b in set_cached); page 2+
# HTMLs are kept only in-memory for parsing.
htmls = [r[0] for r in results]
blocks = [r[1] for r in results]
html_a = htmls[0]  # page 1, meli=False — for cache + parity sample
html_b = htmls[1]  # page 1, meli=True — for cache

block_reason = next((b for b in blocks if b), None)
if block_reason:
    # ... existing block-detected branch unchanged
    pass
```

Downstream, replace:
```python
candidates_a = parse_serp(html_a) if html_a else []
candidates_b = parse_serp(html_b) if html_b else []
all_candidates = candidates_a + candidates_b

```

with:
```python

for h in htmls:
    if h:

all_candidates = dedupe(all_candidates)  # unchanged — by canonical URL
```

## 3. Hipótesis a validar empíricamente con tests

1. **Page 2 HTML estructura es identica a page 1** (mismas clases `div.pla-unit`, `div.Ez5pwe`, etc.) → parser actual funciona sin cambios.
2. **Dedupe-by-URL colapsa duplicates productos identicos entre pages**. Test obligatorio con fixture.
3. **N=2 produce a noticeable gain** sobre saturated queries (electro-espec, ropa-espec, pelota-deporte) — gain target: +10 candidates únicos minimum.

## 4. Riesgos identificados + mitigación

| Riesgo | Probabilidad | Mitigación |
|---|---|---|
| CAPTCHA rate spike sustained porque doblamos fetch volume | Media | `SEARCH_FETCH_PAGES=1` revierte sin redeploy; ChallengeBackoff state existing absorbe spike-and-back-off; monitor con harness |
| Latency p50 sube >50% por 2× fetches | Alta — esperable | Fetches en paralelo via `asyncio.gather` (no serial); cap fetch_serp timeout already 15s; p50 expected to grow ~20-40% no doblar |
| BROWSER_RECYCLE_AFTER=200 deja contextos sin cleanup más rápido | Baja | Cada fetch_serp cierra su context en `finally`; recycle es para recovery, no para health |
| Cache-key change requires migration | N/A | Decisión D-09: cache solo page 1 (status quo) |
| Page 2 HTML structurally diferente (Google a/b) | Baja | Fixture tests congelados verifican; si Google diverge, drift detector lo flagea |
