<domain>
## Phase Boundary

Phase 0.2.1 demostró que 5 de 12 queries del dataset canónico **saturan el shopping panel cap de Google a 30 pla-units en page 1**. Esos 30 son una pared dura por slot que Google sirve — no es problema del parser, es Google capping su panel. Para capturar más productos de queries comerciales densas (electro, ropa, libro, deporte, electronica) hay que pedir **page 2** explícitamente con `&start=10`.

**In scope (PAGE2-01..03):**
1. `build_serp_url(query, meli, page=N)` extendido — emite `&start=10*N` cuando `N > 0`.
2. `/search` lanza **4 fetches paralelos** (A page1, A page2, B page1, B page2) en `asyncio.gather`, sujeto al `GoogleRateLimiter` y al `BROWSER_RECYCLE_AFTER`.
3. Setting `SEARCH_FETCH_PAGES: int = 2` con validator `1 <= x <= 3` para permitir revert rápido a 1 page sin tocar código.
4. Dedupe **pre-LLM** por URL canónica — garantizar que un producto en page 1 + page 2 cuenta una vez (la dedupe actual lo hace por canonicalize_url; aceptamos el existing pero agregamos test que lo prueba).
5. 2 fixtures page-2 HTML (organic-heavy + pla-heavy) frozen en `tests/fixtures/serp/` + integration tests que miden gain incremental real.
6. `Metadata.google_fetches` reporta el número real (era hardcodeado a 2; ahora 2 o 4 dependiente del setting).

**Out of scope explícito:**
- **Page 3+** — el setting hard-caps en 3 pero la implementación foca en page 2 por default. Page 3 es teóricamente posible si Luis sube `SEARCH_FETCH_PAGES=3`, pero no hay tests específicos para esa configuración.
- **Pagination en el endpoint `/search` response** — el consumidor no ve "page" como concepto; sigue recibiendo un flat list de results.
- **Cache key cambia** — el cache de Phase 2 cachea por `(query, query_norm)`, no por `(query, page)`. Si subimos `SEARCH_FETCH_PAGES` el cache hit sigue siendo válido; si bajamos a 1, el cache hit devolverá el set viejo de page 2 hasta que TTL expire. Aceptable: TTL 24h.
- **Adaptive paging** (pedir page 2 solo si page 1 saturó) — sería una optimización siguiente; v0.2.3 hace fetch incondicional cuando `SEARCH_FETCH_PAGES > 1`.
- **Page 2 en `/admin/parity/{q}`** — el endpoint admin sigue evaluando solo page 1 (es para detectar drift del parser, no de paginación). Documentar.
- **Page 2 en el harness sample** — mismo argumento: el sample evalúa lo mismo que el admin endpoint.

<decisions>
## Implementation Decisions

### `build_serp_url` extension
- **D-01:** Agregar parámetro `page: int = 1` (1-indexed) a `build_serp_url`. Backward compat: `page=1` produce exactamente el URL actual (sin `start`). `page=N` para N>=2 agrega `&start=(N-1)*10` (Google convention).
- **D-02:** Validar `1 <= page <= 10` con `ValueError` adentro de la función. Sobre 10 es ya zona de spam-detection de Google y no hay valor real.

### Setting + concurrency budget
- **D-03:** Nuevo setting `SEARCH_FETCH_PAGES: int = 2` con `field_validator` que asegura `1 <= x <= 3`. Sub-3 es un sanity cap: page 3+ aumenta CAPTCHA risk a un nivel donde el spike no ha sido validado.
- **D-04:** `BROWSER_RECYCLE_AFTER` se mantiene en 200 (sin cambio). Con `SEARCH_FETCH_PAGES=2`, cada `/search` usa **4 browser contexts** en vez de 2 — el recycle dispara cada 50 queries en vez de cada 100. Aceptable bajo el tráfico actual (500-2000 q/día). Documentar en el doc string.
- **D-05:** `GoogleRateLimiter` sigue con `GOOGLE_MIN_INTERVAL_S=0` (perf-fix de v0.1). El limiter no es la defensa primaria contra burst — es la `slowapi rate-limit per-API-key` que Phase 3 puso. Sin cambios al rate-limiter.

### `/search` pipeline change
- **D-06:** Reemplazar el bloque `(html_a, block_a), (html_b, block_b) = await asyncio.gather(fetch_serp..., fetch_serp...)` por un loop que arma `N * 2` fetches (N = `SEARCH_FETCH_PAGES`) y los lanza en `asyncio.gather`. Mantener la semántica: si CUALQUIER fetch retorna `block_reason`, todo el response es 503 block (no parcializar — un block_detected en page 2 sigue siendo un block señal genuino).
- **D-07:** El parser corre sobre TODOS los HTMLs recolectados (no solo los page 1). Cada HTML produce su own `parse_serp()` result; los results se concatenan ANTES del `dedupe(all_candidates)` existente.
- **D-08:** `Metadata.google_fetches` se computa dinámico = `N * 2` (era hardcodeado 2). Existing consumers que leen el campo siguen funcionando — el valor sube de 2 a 4 pero la semántica "cuántas fetches a Google hicimos" se mantiene.

### Cache + observability
- **D-09:** `set_cached` recibe `html_a` y `html_b` para audit/replay. Con paginación, tendría que recibir también `html_a_p2`, `html_b_p2`. **Decisión: cachear SOLO page 1** en el storage para mantener compatibilidad con cache existente. Page 2 HTML se re-fetcha en cache miss; en cache hit, solo `html_a`+`html_b` están disponibles. Esto preserva el cache TTL behavior sin schema migration.
- **D-10:** El parity audit sample (`_parity_audit_sample`) y el endpoint `/admin/parity/{q}` siguen evaluando SOLO `html_a` (page 1). NO extender al sample porque (a) el sample mide drift del parser, no de paginación; (b) el HTML cached (page 1) es lo que está disponible barato; (c) doblar el cost del sample anula su low-overhead invariant.

### Dedupe
- **D-11:** El `dedupe()` existente usa `canonicalize_url(url)` como key. La canonicalize ya strippea `utm_*`, `gclid`, fragmentos, etc. Esperamos que un producto MELI que aparece en page 1 y page 2 tenga URL canonicalizable identica → dedupe natural. **Test obligatorio**: integration test que prueba esto con fixtures reales.
- **D-12:** Si el dedupe falla (un producto idéntico aparece con URL distinta page 1 vs page 2), NO se fixea acá — escalar a Phase 0.3 dedupe-by-title fuzzy. Esta phase solo verifica que dedupe-by-URL funciona razonablemente.

### Fixtures + tests
- **D-13:** Capturar 2 fixtures page-2 productivas hoy via Cloak con `wait_until="load"`:
  - `page2_termotanque.html` — la query electro-espec, page 2 (esperado: mucho organic + algo de pla)
  - `page2_zapatillas.html` — la query ropa-espec, page 2 (esperado: solo pla, sin carousel)
- **D-14:** Integration tests:
  - `test_build_serp_url_page2_emits_start_param` — unit
  - `test_search_with_pages_2_makes_4_fetches` — integration con monkeypatch fetch_serp
  - `test_dedupe_collapses_duplicate_url_between_pages` — fixture replay sobre page1 + page2 que comparten un producto
  - `test_metadata_google_fetches_reflects_pages_setting` — value es 2 o 4 según setting

### Smoke runtime (NO autonomous)
- **D-15:** Después de merge, sample manual con `compose up --force-recreate`:
  - `/search` con `termotanque rheem 80 litros electrico` sin paginación (SEARCH_FETCH_PAGES=1): contar results
  - Mismo query con SEARCH_FETCH_PAGES=2: contar results, verificar que > baseline
  - Verificar `metadata.google_fetches=4` en response
- **D-16:** El nightly del harness puede tomar 2× más tiempo después del merge (12 queries × N fetches each); aceptable.

### Claude's Discretion
- **Loop structure exacto** (D-06) — list comprehension `[fetch_serp(...) for page in range(1, N+1) for meli in (False, True)]` vs paired tuples explícitos. Claude decide priorizando legibilidad.
- **Error handling cuando 1 of N fetches falla** (D-06) — si una sola fetch tira excepción, el current behavior es "todo el response 500/empty". Con N fetches, ¿queremos partial-success (extraer de los que funcionaron) o all-or-nothing? Pickear all-or-nothing por consistency con behavior actual; documentar.
- **Nombre exacto del setting** (D-03) — `SEARCH_FETCH_PAGES` sugerido. Si Claude encuentra algo más claro (e.g. `SERP_PAGES_PER_QUERY`), permitir el cambio documentando.

<specifics>
## Specific Ideas

- Google URL convention para page 2: `https://www.google.com/search?q=...&start=10`. Pages 3+: `start=20`, `start=30`, etc.
- Page 2 a veces sirve un set bastante distinto al de page 1; las pla-units pueden ser un subset NUEVO (no necesariamente productos relacionados a los de page 1). Esto justifica el doble fetch en queries que saturan.
- `BROWSER_RECYCLE_AFTER=200` cuenta cada `new_context()`. Con 4 contexts por /search, recycle dispara cada 50 /search calls en vez de 100. Doc: actualizar el comentario inline cerca de la constante.
- `set_cached` recibe `html_a` (string) y `html_b` (string). Si extiendo a 4 strings la cache schema cambia. **Mantener 2 strings** (solo page 1) — esto preserva DB compat.

</specifics>
