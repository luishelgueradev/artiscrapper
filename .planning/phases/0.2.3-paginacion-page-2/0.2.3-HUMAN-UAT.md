## Gaps

### Gap A — `SEARCH_FETCH_PAGES` env passthrough missing in `compose.yml`
status: resolved
discovered: 2026-06-05T21:25:00Z (UAT #2 setup, rollback attempt)
description: Plan 01 added `SEARCH_FETCH_PAGES` to the `Settings` class and documented the env knob in `.env.example`, but `compose.yml` never declared the environment passthrough. The result: setting `SEARCH_FETCH_PAGES=1` in `.env` had zero runtime effect — the container kept reading the pydantic default of 2. This is exactly the cross-layer-shadowing pattern flagged in the user memory `feedback_empirical_retest_after_default_changes`. The rollback recipe advertised in the docstring (CONTEXT D-04: "flip to 1 in env for single-page behavior without a redeploy") was not actually wired.
resolution: commit `3906d13 fix(0.2.3): forward SEARCH_FETCH_PAGES through compose.yml` — env block now reads `- SEARCH_FETCH_PAGES=${SEARCH_FETCH_PAGES:-2}`, verified end-to-end via container recreate + env round-trip (`docker exec ... env | grep SEARCH_FETCH_PAGES` = `1`, settings reload returns `1`).

### Gap B — `wait_until="load"` browser fragility under sustained N×2 pressure
status: follow-up-recommended
discovered: 2026-06-05T21:13:00Z (UAT #2 phase A, 3rd query onwards)
description: Phase 0.2.1's switch from `domcontentloaded` to `load` (to capture Shopping panel `pla-unit` elements) consistently triggers `page.goto` to exceed its 15s timeout when the browser singleton is under sustained 4-context pressure (N×2=4 contexts per request). After the first 2 successful requests, the browser instance dies (`browser_heartbeat_failed`), and subsequent requests return `TargetClosedError` with `candidates_total=0`. Direct in-container Cloak smoke confirms `wait_until="domcontentloaded"` still returns valid 411 KB SERPs in <2s — the failure is specifically with the `load` wait, not with Google's defenses or any block. This is a pre-existing 0.2.1 fragility exposed faster by 0.2.3's doubled fetch count; not a 0.2.3 regression per se.
recommendation:
  - Option 1 (fast): bump per-fetch timeout from 15s → 30s in `browser.fetch_serp` — masks the symptom, keeps `wait_until="load"` for pla-unit fidelity
  - Option 2 (correct): replace `wait_until="load"` with `wait_until="domcontentloaded"` + explicit wait for the pla-unit container selector (`page.wait_for_selector("div.pla-unit", timeout=10000)`) — slimmer, deterministic, no dependency on Google's image/font/script load timing
  - Option 3 (deep): N-fetch concurrency limiter — `asyncio.Semaphore(2)` around the gather loop so even with N=2 we only run 2 contexts in flight; trades a small latency hit for browser stability
  - Suggested phase: open as standalone bug or fold into 0.2.4 (SerpAPI spike — partially overlaps if SerpAPI replaces the Cloak fetch path for some queries) or 0.2.5 (carried tech debt). Filed observation references for the next planner: `feedback_empirical_retest_after_default_changes`, `feedback_compose_build_recreate`, CONTEXT D-04 (BROWSER_RECYCLE_AFTER unchanged at 200 but only 50 N×2 queries before recycle).

### Gap C — Exception-path `google_fetches` reports the pydantic default instead of the actual count
status: cosmetic-follow-up
discovered: 2026-06-05T21:13:39Z (UAT #2 phase A, libro-broad onwards)
description: When `asyncio.gather` raises (TargetClosedError / TimeoutError), the exception handler at `main.py:752-760` returns `Metadata(elapsed_ms=..., cache_hit=False, block_detected=False)` — relying on the pydantic default `google_fetches: int = 2` (per `models.py:43`). Observable effect: a fully-blown TargetClosedError response advertises `google_fetches=2` even though zero pages were successfully fetched. Honest-but-misleading.
recommendation: small follow-up — pass `google_fetches=0` explicitly in the exception path; or update the default to 0 and require successful paths to set it (more invasive). One-line cosmetic fix in the exception block.
