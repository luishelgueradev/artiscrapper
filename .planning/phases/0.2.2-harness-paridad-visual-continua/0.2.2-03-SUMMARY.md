# Plan 0.2.2-03 — CI Nightly + Prometheus Alerts — Summary

## Goal

Close Phase 0.2.2 with the automation surface: a scheduled CI job that
audits the canonical dataset and fails on threshold breach, plus
Prometheus alert YAML ready for pickup when a Prometheus server is
deployed.

## What was built

### 1. `scripts/run_parity_nightly.py` (HARNESS-04)

Standalone CLI runner invoked by the GitHub Actions workflow. Reads the
canonical 12-query dataset YAML, calls `/admin/parity/{q}` for each entry
with 1-second polite spacing, aggregates per-query coverage_pct, prints a
markdown summary, and exits:

- `0` — all queries answered AND avg coverage ≥ threshold
- `1` — at least one blocked query OR no measurements OR avg < threshold

CLI flags:
```
--dataset PATH       YAML dataset path
--endpoint URL       Base URL for /admin/parity
--api-key KEY        X-API-Key value
--threshold FLOAT    Failure threshold (default 75.0)
--summary PATH       Optional markdown output file
```

Uses `urllib` + `json` for the HTTP layer; `PyYAML` for the dataset; pure
stdlib for everything else. Lazy `yaml` import so helper functions
(`_row`, `_to_markdown`) are unit-testable without YAML side effects.

### 2. `tests/test_run_parity_nightly.py` — 5 unit tests (HARNESS-04)

- `test_row_ok_status_when_coverage_above_50` — coverage ≥ 50 → OK
- `test_row_low_status_when_coverage_below_50` — coverage < 50 → LOW
- `test_row_blocked_query` — blocked response → BLOCKED: …
- `test_row_error_query` — network exception → ERROR: …
- `test_markdown_table_includes_header_and_rows` — table renders fields + threshold

### 3. `.github/workflows/parity-nightly.yml` (HARNESS-04)

GitHub Actions workflow with two triggers:
- `schedule: "0 3 * * *"` (3am UTC, midnight ART — low-traffic window)
- `workflow_dispatch: {}` (manual run via the Actions UI)

Pipeline steps:
1. Verify `ARTISCRAPPER_NIGHTLY_KEY` secret is set (fail fast)
2. Set up Python 3.12 + uv + project deps
3. `docker compose build` (uses production Dockerfile)
4. `docker compose up -d` with secret passed through `API_KEYS` env
5. Wait for `/health` to return 200 (90s grace period for Cloak boot)
6. Run `scripts/run_parity_nightly.py` against the dataset; output to
   `$GITHUB_STEP_SUMMARY` (shows in the Actions UI)
7. `docker compose logs --tail=200` on failure
8. `docker compose down --volumes` always (free runner space)

`LLM_ROUTER_BEARER_TOKEN` is given a `ci-nightly-placeholder` value
since the parity endpoint doesn't exercise the LLM router — only the
lifespan boot needs the token present.

Workflow does NOT block PRs (scheduled-only). Failed runs notify via
the default GitHub subscription.

### 4. `prometheus/alerts/parity.yaml` — 3 alert rules (HARNESS-05)

Three rules ready for pickup when a Prometheus server is deployed:

| Alert | Expr | For | Severity |
|---|---|---|---|
| `ParityCoverageWarn` | `avg_over_time(coverage_pct[30m]) < 75` | 30m | warning |
| `ParityCoverageFail` | `avg_over_time(coverage_pct[5m]) < 50` | 5m | critical |
| `ParityPlaUnitsMissed` | `increase(pla_units_missed_total[15m]) > 5` | 5m | warning |

Each alert annotation includes an actionable runbook hint:
- WARN includes the curl command to spot-check the query
- FAIL ranks probable causes (class rotation, upstream Cloak, CAPTCHA)
- PlaMissed names the specific obfuscated classes likely to have rotated

NO Alertmanager routing — Slack/email/PagerDuty integration is Phase 4
production-ops territory.

## Deviations

None significant. PyYAML parses YAML's `on:` key as boolean `True` (Norway
problem variant) — this is a known YAML 1.1 quirk and does not affect
GitHub Actions which uses its own parser. The workflow file is valid for
GitHub Actions.
