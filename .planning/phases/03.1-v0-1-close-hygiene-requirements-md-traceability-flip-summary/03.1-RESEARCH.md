## §1: slowapi Settings-source-of-truth pattern (D-05)

### Current state (the bug)

`src/artiscrapper/main.py:354-362`:

```python
@app.post("/search", response_model=SearchResponse)
@limiter.limit("60/minute")     # ← hardcoded string
@limiter.limit("10000/day")     # ← hardcoded string
async def search(
    request: Request,
    response: Response,
    body: SearchRequest,
    _api_key: str = Depends(verify_api_key),
) -> SearchResponse:
```

`src/artiscrapper/config.py:46-47`:

```python
API_RATE_PER_MINUTE: int = 60
API_RATE_PER_DAY: int = 10000
```

`src/artiscrapper/main.py:172-176` (the **lie**):

```python
log.info(
    "rate_limit_init",
    per_min=settings.API_RATE_PER_MINUTE,  # logs settings, not decorator
    per_day=settings.API_RATE_PER_DAY,
)
```

**The shadowing:** If an operator sets `API_RATE_PER_MINUTE=120` in `.env` and runs `compose up --force-recreate`, the log line happily prints `per_min=120` while the decorator is still enforcing `60/minute`. This is the exact class of bug `feedback_empirical_retest_after_default_changes` was filed against in Phase 2.

`src/artiscrapper/main.py:240` (the Limiter):

```python
limiter = Limiter(key_func=get_api_key, headers_enabled=True)
```

### Four candidate patterns evaluated

| # | Pattern | Verified via | Survives `compose up --force-recreate`? | Honest `rate_limit_init`? | Test impact |
|---|---------|--------------|------------------------------------------|--------------------------|-------------|
| **A** | **`default_limits=[...]` on `Limiter()` constructor** | [VERIFIED: Context7 /laurents/slowapi — "Apply Application-Wide Rate Limits"] | ✅ values are baked at import | ✅ log line reads from the same module constants | Tests stop using `@limiter.limit(...)` on the route → must remove inline decorators |
| B | f-string at decorator: `@limiter.limit(f"{settings.API_RATE_PER_MINUTE}/minute")` | [VERIFIED: standard Python; slowapi accepts any str at decorator] | ✅ | ⚠️ log emits settings, decorator emits f-string — same source but two render sites | Minimal — decorators stay |
| C | Callable: `@limiter.limit(lambda: f"{settings.API_RATE_PER_MINUTE}/minute")` | [VERIFIED: Context7 /laurents/slowapi — "Dynamic limits without key dependency"] | ✅ | ⚠️ runs per request (cost) | Decorators stay, but each invocation re-evaluates |
| D | `slowapi.parse_many("60/minute;10000/day")` + manual storage push | [ASSUMED] — no Context7 entry for direct parse_many usage | ⚠️ undocumented private API | ⚠️ requires custom log call | Brittle; would not survive slowapi 0.2 |

### Chosen pattern: A — `default_limits` on the `Limiter()` constructor

**Rationale (preferring permanent + idiomatic):**

1. **Idiomatic:** Context7's official "Apply Application-Wide Rate Limits" example is literally this pattern. It's the documented way to express "all routes share these caps."
2. **Single source of truth:** The same module-level constants flow into BOTH the `Limiter()` constructor AND the `rate_limit_init` log line. The log cannot lie about the decorator because the decorator no longer exists — the `Limiter` enforces the limits intrinsically.
3. **Survives `compose up --force-recreate`:** All values are resolved at import time from `settings`, which `pydantic-settings` reloads from the new env on each container start.
4. **Test impact is minimal:** `tests/integration/test_rate_limit.py` exercises `/search` 60+ times via TestClient against the same app singleton — it does not care whether the limit came from a decorator or from `default_limits`. Reset via `app.state.limiter.reset()` still works (it always operated at the `Limiter` level, not the decorator level).
5. **No callable overhead:** Settings are import-time-frozen by design (`pydantic-settings` caches at first `Settings()` call). A callable limit form would add per-request work without giving us anything we don't already have.

### Reference implementation

**`src/artiscrapper/main.py` (proposed)** — three changes, ~10 LOC delta:

```python
# 1. NEW: module-level constants computed once from settings.
#    These are the SINGLE source of truth for the rate-limit values.
#    The lifespan log line below + the Limiter() constructor BOTH read
#    from these constants — drift between log and runtime is impossible
#    by construction (single source).
_RATE_LIMIT_PER_MINUTE = f"{settings.API_RATE_PER_MINUTE}/minute"
_RATE_LIMIT_PER_DAY = f"{settings.API_RATE_PER_DAY}/day"
_RATE_LIMITS = [_RATE_LIMIT_PER_MINUTE, _RATE_LIMIT_PER_DAY]

# 2. CHANGED: Limiter constructor — default_limits applies to every route.
#    The order in the list is the order of evaluation; first-to-fire wins
#    (matches existing stacked-decorator semantics).
limiter = Limiter(
    key_func=get_api_key,
    default_limits=_RATE_LIMITS,
    headers_enabled=True,
)

# 3. REMOVED: the two stacked @limiter.limit() decorators on /search.
#    default_limits applies to ALL routes — including /search, /health,
#    /health/deep. We need to OPT OUT the health endpoints so cheap
#    liveness probes don't consume the /search quota:
@app.get("/health")
@limiter.exempt          # ← NEW: liveness must never be rate-limited
async def health(request: Request) -> dict:
    ...

@app.get("/health/deep")
@limiter.exempt          # ← NEW: deep health is auth-gated; quota not appropriate
async def health_deep(request: Request, _api_key: str = Depends(verify_api_key)) -> dict:
    ...

# /metrics is already an ASGI sub-app (mounted, not a FastAPI route) so
# default_limits does NOT apply to it — D-10 invariant preserved without
# any change.

# 4. CHANGED: lifespan log line reads from the SAME constants so the
#    grep target `rate_limit_init` cannot diverge from the running
#    decorator value:
log.info(
    "rate_limit_init",
    per_minute=_RATE_LIMIT_PER_MINUTE,   # full string, "120/minute"
    per_day=_RATE_LIMIT_PER_DAY,         # full string, "10000/day"
    source="default_limits",             # provenance tag for forensics
)
```

### Why this is the permanent fix (vs. a wrapper / logging fix)

- The alternative "log the actual decorator strings" merely makes drift *visible*; it does not eliminate it. The next env bump would still require an engineer to notice the log mismatch.
- The `default_limits` pattern makes drift *structurally impossible*: there is exactly one place in the codebase where `"60/minute"` is constructed (or `"120/minute"` after bump), and both the Limiter and the log line consume that string.
- It survives upgrade to slowapi 0.2+ because `default_limits` is part of the documented public API, not a private parsing helper.

### Import-time vs request-time tradeoff (locked)

Pattern A binds values at **import time**. In this app:
- Container start → pydantic-settings reads `.env` → `settings.API_RATE_PER_MINUTE` is set → module-level constants compute → `Limiter` constructed with `default_limits`.
- The hot path never re-evaluates the limit string.

This matches the existing app architecture (`settings` is treated as immutable per-process). If a future requirement says "rotate quotas without restart," that's a Phase 4/5 change (distributed store + admin endpoint, already deferred). Phase 3.1 stays scoped to "fix the drift, do not change the runtime contract."

### Risks

- **R1:** `@limiter.exempt` is required on `/health` and `/health/deep` because `default_limits` is global. Forgetting it would cause `/health` to consume the same 60/min bucket as `/search`. Tests must include: `pytest tests/test_health.py -x -q` after the refactor, and ideally a new `test_health_not_rate_limited` that hits `/health` 70 times and asserts no 429s. [Recommendation: planner adds this as a Wave 0 invariant.]
- **R2:** `_RATE_LIMITS` is a module-level list of f-strings. Engineers reading the diff might think "this is a constant" and try to mutate it — add a comment that it is computed from settings and not editable at runtime.
