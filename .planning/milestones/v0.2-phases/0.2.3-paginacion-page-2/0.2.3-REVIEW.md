# Phase 0.2.3: Code Review Report

**Reviewed:** 2026-06-05
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

Phase 0.2.3 adds optional N-page SERP pagination to `/search`, controlled by `SEARCH_FETCH_PAGES` (default 2, max 3). The implementation is cleanly scoped: `build_serp_url` accepts a `page` kwarg with proper bounds-checking, the main pipeline replaces a hardcoded 2-fetch `gather` with an N×2 loop, and integration tests cover both the new default and the v0.2.2 revert path.

No critical correctness defects or security regressions were found. The principal concerns are:

1. A **rate-limiter deadlock risk** that becomes exploitable any time `GOOGLE_MIN_INTERVAL_S` is raised above 0 — the new N×2 fetch loop serializes through a `Semaphore(1)` instead of running in parallel, so cold-path latency can balloon to `N×2×interval` seconds, which on the default cap (`SEARCH_FETCH_PAGES=3`, e.g. 60s) is a 6-minute synchronous wait inside an HTTP handler. This silently undoes the BROWSER-04 perf fix when an operator sets a non-zero floor.
2. **Page-2+ HTML is not persisted to cache** — only `html_a` / `html_b` (page-1) flow into `set_cached`. A cache hit will replay only page-1 candidates, so the post-Phase-0.2.3 user-visible result count silently degrades 24h after first capture. This is a quiet contract drift between the fetch loop and the cache schema, not a crash.
3. The `_fake_fetch_factory` in `test_search_paginated.py` matches the page-2 marker via `"start=10" in url` — a substring match that is also true for `start=100/start=101…/start=10X`. Today no other code emits those values, but a future `page=11` raising `ValueError` is the only thing preventing a misroute. Tighten to `&start=10&` or use `urlparse`.
4. Several smaller items: dead `block_detected = False` initializer, unused `page` parameter validation message inconsistency between the `<= 10` cap and the `<= 3` cap in `SEARCH_FETCH_PAGES`, and a fixture-capture script that uses `wait_until="load"` without retry while the integration tests assume the fixture exists.

The phase is shippable, but BLOCKER fixes (WR-01, WR-02) should be done before any production deploy where the operator is tempted to bump the rate-limiter floor.

## Warnings

### WR-01: Rate-limiter `Semaphore(1)` serializes the N×2 fetches — silent latency cliff when `GOOGLE_MIN_INTERVAL_S > 0`

**File:** `src/artiscrapper/main.py:743-760` (fetch loop) + `src/artiscrapper/rate_limit.py:20-30`
**Issue:** The fetch loop builds N×2 coroutines and runs them through `asyncio.gather`, but every `fetch_serp` call ends up taking the `GoogleRateLimiter._sem` (`asyncio.Semaphore(1)`) and then sleeping for the residual interval. With `GOOGLE_MIN_INTERVAL_S=0` (the new default) this is fine — but the env var still exists and is documented in `.env.example`, and the per-page comment says the cap is 3 ("BROWSER_RECYCLE_AFTER + CAPTCHA-risk safety"). If an operator restores the historical 60s floor (or even 5s) to dodge a burst-block, the cold path becomes:
- N=2: 4 fetches × 60s = 240s wall-clock, inside `with search_elapsed.time()` and inside a single HTTP request, well past most LB / nginx idle timeouts (60–120s).
- N=3: 6 × 60s = 360s = 6 minutes.

The pre-Phase-0.2.3 code had the same shape (2 serialized fetches) but only paid 2×interval. The N×2 loop turns a linear cost into a multiplier without surfacing it anywhere. `GOOGLE_MIN_INTERVAL_S=0` is load-bearing for this phase — it should be acknowledged in the docstring on `SEARCH_FETCH_PAGES`, or the loop should fan out per-page (parallel) while keeping per-fetch-pair serialized.

**Fix:** Add a deployment guard or document the multiplicative cost. Minimal fix in `config.py`:
```python
@field_validator("SEARCH_FETCH_PAGES")
@classmethod
def _validate_search_fetch_pages(cls, v: int) -> int:
    if not 1 <= v <= 3:
        raise ValueError(f"SEARCH_FETCH_PAGES must be in [1, 3], got {v}")
    return v
```
Should additionally reject `v > 1 and GOOGLE_MIN_INTERVAL_S > 5` (cross-field validation in a `model_validator`), or the docstring on `GOOGLE_MIN_INTERVAL_S` should state "raising this above 0 multiplies cold-path latency by `SEARCH_FETCH_PAGES * 2`". The cleanest engineering fix is to make the rate-limiter aware of "this is a single /search burst" so the N fetches in one request share one gate.

### WR-02: Page-2+ HTML is dropped before cache write — cache hits silently downgrade to page-1-only results

**File:** `src/artiscrapper/main.py:766-769, 980-985`
**Issue:** The fetch loop collects all N×2 HTMLs into `htmls` (line 762), but only `html_a = htmls[0]` and `html_b = htmls[1]` are forwarded to `set_cached` (line 982-983). The cache schema (`raw_serp_html_a` / `raw_serp_html_b`, cache.py:35-36) was designed for the 2-fetch model. The candidate `results` list written to the cache row was built from all N pages (parse_serp loops over `htmls` at line 817-819), so the JSON response replay is fine — but any downstream consumer that does a `get_cached`-and-re-parse loop (the parity audit hot path explicitly does this via `html_a` only, line 999-1006) will see only page-1 signals. The parity gauges `parity_pla_in_html` and `parity_pla_extracted` will drift downward by ~50% between cache misses and cache hits, breaking the parity-drift alert HARNESS-05 was designed to fire.

Also: cache TTL is 24h. For 24 hours after first capture, the user gets a JSON response with N-page candidates but the cached HTML is page-1-only. There is no log signal indicating which page-set produced the cached body, so reproducing a "this candidate was X yesterday" question becomes impossible.

**Fix:** Either (a) extend the cache schema to store all `htmls` (BLOB array or JSON list), or (b) document explicitly in the `set_cached` callsite that "raw_serp_html_a/b is the page-1 sample only; the parity sample task should read it as such":
```python
# Page-1 HTMLs only — cache schema predates pagination (cache.py:35-36).
# Page 2+ candidates ARE in `results`, but the raw HTML is not persisted.
# Parity sample reads html_a (page-1) and reports page-1 pla counts; the
# discrepancy is intentional as of Phase 0.2.3 and tracked under PAGE2-FOLLOWUP.
await set_cached(
    ...,
    html_a=html_a,
    html_b=html_b,
)
```
The fast path is (b) with a follow-up ticket; the durable path is (a).

### WR-03: Test substring match `"start=10" in url` is loose — also matches `start=100..109`

**File:** `tests/integration/test_search_paginated.py:130, 206, 246`
**Issue:** `_fake_fetch_factory.fake_fetch` routes to the page-2 fixture when `"start=10" in url`. The pagination contract is `start = (page-1) * 10`, so today valid page numbers produce `start=10/20/30/.../90`. The substring `"start=10"` also matches `start=100` (page 11), `start=109`, etc. — these aren't reachable now because `build_serp_url` rejects `page > 10` with `ValueError`, but the test asserts the runtime contract via a much weaker check than the code enforces. If anyone ever relaxes the `page <= 10` cap (the docstring says "Page 11+ raises ValueError — beyond that is Google spam-detection territory"), the test silently misroutes.

The page-2-URL-count assertion at line 207 (`page2_calls = [u for u in fake.call_log if "start=10" in u]`) has the same issue.

**Fix:**
```python
async def fake_fetch(browser, url, rate_limiter):
    call_log.append(url)
    # Match `start=10` as a whole query parameter, not as a substring (start=100 would match).
    qs = parse_qs(urlparse(url).query)
    if page2_html is not None and qs.get("start") == ["10"]:
        return page2_html, None
    return page1_html, None
```
Apply the same `urlparse + parse_qs` form to the assertion at line 206 and the regression-guard assertion at line 246.

### WR-04: Dead initializer `html_a, html_b = "", ""` always immediately overwritten

**File:** `src/artiscrapper/main.py:754`
**Issue:** Lines 754 set `html_a, html_b = "", ""` before the try block, but the try block (lines 760-769) unconditionally overwrites both on success. On the `except` branch (line 770), the code returns early without using `html_a` or `html_b`. The initializers are dead. This is a minor code-smell but also a confusing read: someone editing the except branch might assume "html_a and html_b are empty strings at this point" is a reachable post-condition.

**Fix:**
```python
htmls: list[str] = []
blocks: list[str | None] = []
block_detected = False

try:
    fetch_results = await asyncio.gather(*fetch_coros)
    request.app.state.browser_uses += len(fetch_coros)
    htmls = [r[0] for r in fetch_results]
    blocks = [r[1] for r in fetch_results]
    html_a = htmls[0] if htmls else ""
    html_b = htmls[1] if len(htmls) > 1 else ""
except Exception as exc:
    log.warning("google_fetch_failed", error=str(type(exc).__name__))
    ...
```
Move `html_a/html_b` declaration into the try block where it's actually computed.

### WR-05: `block_detected = False` initialized but reassigned in only one branch — dead assignment on the happy path

**File:** `src/artiscrapper/main.py:757, 786`
**Issue:** `block_detected = False` is set at line 757, then reassigned to `True` at line 786 inside the `if block_reason:` branch (which returns immediately on line 805). The happy path (no block) never touches `block_detected` after line 757 until it's read at line 1020. This works, but it's confusing because the variable has no second writer outside the block branch — the local could be replaced with `False` literal at the response-construction site, or, conversely, dropped entirely (the `if block_reason:` branch already returns before reaching the response builder at line 1008).

**Fix:** Either remove the line-757 initializer and read `False` at the response site:
```python
return SearchResponse(
    ...,
    metadata=Metadata(
        ...,
        block_detected=False,  # block path early-returns above
    ),
)
```
Or delete the dead reassignment at line 786 since the early return makes it unreachable from the response-builder POV.

### IN-04: `scripts/capture_page2_fixtures.py` lacks the `wait_until="load"` justification + uses 15s timeout

**File:** `scripts/capture_page2_fixtures.py:58`
**Issue:** Uses `wait_until="load"` with 15_000ms timeout. The shopping panel memory note says `pla-unit` requires `wait_until="load"` specifically. That decision is load-bearing for fixture quality (a partially-loaded page produces a fixture that test_parse_serp_page2_*_fixture passes at the floor=10 boundary but represents a degraded SERP). # wait_until="load" is required — shopping panel (pla-unit) DOM is

```python
# See memory: project_shopping_panel_pla_unit.md.
await page.goto(url, wait_until="load", timeout=15_000)
```

### IN-06: Comment lies about contents of `htmls` — "Page-1 HTMLs are at index 0 (non-meli) and 1 (meli)" depends on loop order

**File:** `src/artiscrapper/main.py:766-768`
**Issue:** Comment asserts page-1 HTML is at indices 0 and 1. This is true only because the outer loop is `for page in range(1, N+1)` and the inner is `for meli in (False, True)` — flip the loop nesting and the comment becomes wrong silently. The comment encodes a property that the loop structure happens to satisfy. The actual extraction (`htmls[0]`, `htmls[1]`) re-encodes the same assumption a second time. If you ever want to fan-out per page (parallel) and join per pair (serial), the indexing is incorrect.

**Fix:** Track page-1 HTMLs by an explicit predicate:
```python
fetch_coros = []
fetch_meta = []  # parallel list of (page, meli) tuples
for page in range(1, N + 1):
    for meli in (False, True):
        fetch_coros.append(
            fetch_serp(browser, build_serp_url(body.query, meli=meli, page=page), rate_limiter)
        )
        fetch_meta.append((page, meli))

fetch_results = await asyncio.gather(*fetch_coros)
htmls = [r[0] for r in fetch_results]
blocks = [r[1] for r in fetch_results]
# Explicit page-1 picks (cache schema: html_a = non-meli p1, html_b = meli p1).
html_a = next((h for h, (p, m) in zip(htmls, fetch_meta) if p == 1 and not m), "")
html_b = next((h for h, (p, m) in zip(htmls, fetch_meta) if p == 1 and m), "")
```
