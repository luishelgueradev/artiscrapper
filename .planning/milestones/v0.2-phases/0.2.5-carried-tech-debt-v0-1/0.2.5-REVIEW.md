## Warnings

### WR-01: `_host_from_url` uses `str.lstrip("www.")` which is char-set-based, not prefix-based

**File:** `scripts/spike/09_label_cards.py:182`
**Issue:** `m.group(1).lstrip("www.")` strips ANY combination of the characters `w`, `.` from the LEADING edge of the host string, not the literal prefix `www.`. Concrete misbehavior:
- `"weather.example.com".lstrip("www.")` -> `"eather.example.com"` (chops the `w`).
- `"wwww.example.com".lstrip("www.")` -> `"example.com"` (acceptable accidentally).
- `"www.google.com".lstrip("www.")` -> `"google.com"` (works by coincidence).

This corrupts the host used as the `expected_store_hint` source in `_auto_label` (line 248, 254, 263, 277), polluting labelled fixtures whenever a host begins with `w`. Eight of the QUERIES touch automotive part hosts; any host starting with `w` (e.g., `walmart.com.ar`) would produce a wrong `store_hint`. Phase 0.2.5 did not introduce this bug (it pre-existed back to commit 876fa88), but the file is in scope for review and this is the only logic defect I found in the reviewed set.

**Fix:**
```python
def _host_from_url(url: str) -> str:
    """Extract hostname from URL, stripping a leading 'www.' if present."""
    m = re.match(r'https?://([^/]+)', url)
    if not m:
        return ""
    host = m.group(1)
    return host[4:] if host.startswith("www.") else host
```

Equivalently use `urllib.parse.urlparse(url).hostname.removeprefix("www.")` (Python 3.9+; project pins 3.12).

### WR-02: `filterwarnings = ["error::DeprecationWarning"]` is a blanket; verify no third-party dep silently regresses CI

**File:** `pyproject.toml:44-46`
**Issue:** Promoting `DeprecationWarning` to `error` for the entire test suite means ANY transitive dep that fires a deprecation warning during collection or test execution will break the build. Today the full quick suite passes (verified: 124/124 with the gate on). This is the documented intent. The risk is that a future bump of `aiosqlite`, `selectolax`, `cloakbrowser`, `pydantic`, or `prometheus-client` ships a `DeprecationWarning` and the gate fires opaquely — a `pytest -W` filter inverted to `error` provides no information beyond "something deep in lib X is deprecated". Compare to the Plan-03 approach of narrow ignores keyed by message.

This is not a bug — it is the documented Phase 0.2.5 success criterion (`pytest -q -W error::DeprecationWarning -m "not slow"` exits 0). Recording it as a Warning so the next dep bump operator knows the failure surface to expect.

**Fix:** Either accept the trade-off (current state — recommended per the SUMMARY), or add a documented narrow-ignore escape hatch:
```toml
filterwarnings = [
    "error::DeprecationWarning",
    # Future narrow escapes: only for trusted third-party noise, never for ours.
    # "default::DeprecationWarning:some_third_party_module",
]
```
