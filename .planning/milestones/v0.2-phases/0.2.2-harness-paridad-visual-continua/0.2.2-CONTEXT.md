## Phase Boundary

Esta phase **construye encima** del endpoint `/admin/parity/{query}` y las 2 gauges Prometheus que Phase 0.2.1 dejó listas (PARITY-05). El objetivo es transformar ese endpoint manual en un **harness automático que detecta drift sin que un humano tenga que mirar**.

Drift en este contexto = cualquier evento donde el parser deja de reflejar lo que Google sirve. Ejemplos:
- Google rota la clase `VbBaOe` → `_extract_pla_unit` retorna `None` → drift detector flagea `pla_unit_in_html_not_extracted`.
- Google cambia el contenedor `div.pla-unit` → 0 pla en HTML → coverage cae en queries que históricamente tienen alta densidad de pla.
- Cambios upstream en `wait_until="load"` empiezan a perder bloques.

**In scope (HARNESS-01..05):**
1. Dataset canónico de 12 queries cross-vertical persistido en repo (`tests/fixtures/parity-dataset.yaml` o equivalente JSON).
2. 3 métricas Prometheus completas: `parity_coverage_pct{query}`, `parity_pla_units_missed{query}`, `parity_url_synthetic_ratio{query}`.
3. Sample asincrónico 1/10 sobre tráfico productivo de `/search` con overhead p99 <50ms medible.
4. CI nightly GitHub Actions workflow `parity-nightly.yml` que corre el dataset completo y falla si coverage promedio <75%.
5. Alertas Prometheus `ParityCoverageWarn` (75% por >30min) y `ParityCoverageFail` (50% por >5min) declaradas en `prometheus/alerts/parity.yaml`.

**Out of scope explícito:**
- **Estrategia B** (DOM-driven browser persistente) — sigue out-of-scope post-v0.1.
- **Page 2 pagination** — Phase 0.2.3 (depende de 0.2.1, NO depende de 0.2.2).
- **SerpAPI integration** — Phase 0.2.4 (puede o no llegar; conditional).
- **Cambios estructurales al parser** — Phase 0.2.1 cerró Estrategia A; 0.2.2 NO toca `search.py` ni `browser.py` salvo el sample 1/10 wire-in.
- **UI de auditoría** — el endpoint devuelve JSON; ningún dashboard custom en este scope (Grafana/Prometheus boards son Phase 4).
- **Alertas a Slack/email/PagerDuty** — Prometheus declarations sí; routing a destinos humanos NO (es Phase 4 production-ops).

## Implementation Decisions

### Dataset canónico (HARNESS-01)
- **D-01:** Persistir en `tests/fixtures/parity-dataset.yaml` (YAML por legibilidad humana — el dataset va a evolucionar y los reviewers necesitan editarlo cómodo). Schema mínimo: `id`, `query`, `vertical`, `specificity` (`espec` | `broad`), `min_expected_real_urls` (umbral por-query), `notes`.
- **D-02:** Las 12 queries son las del reporte (validadas empíricamente 5 ya, otras 7 derivadas con el mismo patrón 6 verticales × 2 niveles):
  ```
  toy-coleccion      / "figura coleccion robotech"
  toy-broad          / "lego juguete niño"
  auto-espec         / "filtro aceite ford focus 2.0 2018"
  auto-broad         / "bujia ngk corolla"
  electro-espec      / "termotanque rheem 80 litros electrico"
  electro-broad      / "heladera samsung"
  ropa-espec         / "zapatillas nike air max hombre 42"
  ropa-broad         / "remera basquet"
  libro-espec        / "harry potter piedra filosofal tapa dura"
  libro-broad        / "libro programacion python"
  pelota-deporte     / "pelota futbol adidas n5"
  electronica        / "auriculares sony wh-1000xm5"
  ```
- **D-03:** `min_expected_real_urls` por-query se establece a partir de la primera corrida exitosa del dataset (snapshot 2026-06-05 productivo). Valor inicial: 50% del valor medido en la primera corrida. Razón: las pla-units son volátiles; un threshold absoluto castiga rondas con bajo auction de Google.

### Métricas Prometheus completas (HARNESS-02)
- **D-04:** 3 gauges nuevas en `src/artiscrapper/metrics.py` (al lado de las 2 de Phase 0.2.1):
  - `artiscrapper_parity_coverage_pct{query}` — pct de URLs reales esperadas vs encontradas (0.0-100.0)
  - `artiscrapper_parity_pla_units_missed{query}` — counter monótono que sube cuando `pla_in_html > pla_extracted` (drift signal hardcoded)
  - `artiscrapper_parity_url_synthetic_ratio{query}` — fraction de candidates que tienen URL `google.com/search?q=...` sobre total candidates con URL (alto = mucho carousel sin resolver)
- **D-05:** Coverage_pct se computa como `100 * candidates_real_url / min_expected_real_urls` con clamp a 100. `pla_units_missed` sube cuando `pla_in_html > pla_extracted` y se loguea con `structlog.warning("parity_drift_detected", query=..., expected=..., got=...)` para tener señal humana correlacionable.
- **D-06:** Métricas se setean tanto desde `/admin/parity/{q}` (manual + nightly) como desde el sample hot-path (productivo). El label `query` se trunca a 80 chars (igual que Phase 0.2.1).

### Sample asincrónico 1/10 sobre hot path (HARNESS-03)
- **D-07:** En `src/artiscrapper/main.py`, dentro de `POST /search`, después de cachear el resultado, schedule un `asyncio.create_task(_parity_audit_sample(query))` con 1/10 probabilidad (controlada por env `PARITY_SAMPLE_RATE=0.1`).
- **D-08:** `_parity_audit_sample` corre la misma lógica del endpoint `/admin/parity/{q}` PERO REUSA el HTML que ya está cacheado (cache hit del `/search` original). NO hace fetch fresh a Google. Esto es lo que mantiene overhead <50ms — solo parser + comparación sobre HTML ya disponible.
- **D-09:** El sample task NO bloquea la response de `/search`. Está fire-and-forget con `BG_TASKS` strong-ref pattern (igual que el cache-write bg task de Phase 2 WR-02). Si falla, loguear `parity_sample_failed` warning, no propagar excepción.
- **D-10:** Settings: agregar `PARITY_SAMPLE_RATE: float = 0.1` con validator `0.0 <= x <= 1.0`. Setting a `0.0` desactiva el sample por completo (útil en tests).

### CI nightly (HARNESS-04)
- **D-11:** GitHub Actions workflow `.github/workflows/parity-nightly.yml`:
  - Cron `0 3 * * *` (3am UTC = 0am ART aprox, ventana de baja carga)
  - `docker compose build` + `docker compose up -d`
  - Espera healthcheck OK (timeout 90s — Cloak bootea ~45s)
  - Loop sobre las 12 queries: `curl /admin/parity/{q}` con X-API-Key (env-secret)
  - Agrega `coverage_pct` por-query, computa promedio, falla si `<75`
  - Output: summary table en GitHub Actions UI + métricas Prometheus pusheadas (opcional, defer si no hay pushgateway)
- **D-12:** El API key del nightly va en `GITHUB_SECRETS.ARTISCRAPPER_NIGHTLY_KEY` para mantener separation con prod keys. Si el secret no existe, el workflow falla con mensaje claro.
- **D-13:** Workflow no bloquea PRs (es scheduled-only). Failed runs notifican vía la suscripción default de GitHub. NO integramos con Slack/email/PagerDuty en este scope.

### Alertas Prometheus (HARNESS-05)
- **D-14:** Declarar las 2 alertas en `prometheus/alerts/parity.yaml`:
  ```yaml
  - alert: ParityCoverageWarn
    expr: avg_over_time(artiscrapper_parity_coverage_pct[30m]) < 75
    for: 30m
    labels: { severity: warning }
    annotations:
      summary: "Parity coverage degraded for {{ $labels.query }}"
      description: "{{ $value }}% coverage < 75% threshold over 30min"
  - alert: ParityCoverageFail
    expr: avg_over_time(artiscrapper_parity_coverage_pct[5m]) < 50
    for: 5m
    labels: { severity: critical }
    annotations:
      summary: "Parity coverage CRITICAL for {{ $labels.query }}"
  ```
- **D-15:** El archivo `prometheus/alerts/parity.yaml` es solo declaración; la integración con un Prometheus server / Alertmanager activo es Phase 4 production-ops. Esta phase deja las alertas listas para ser pickup-eables sin trabajo adicional.

## Specific Ideas

- Las 5 queries productivas testeadas hoy (5/6) dieron coverage real:
  ```
  figura+coleccion+robotech   → 18 real URLs  (mín esperado 9 = 50%)
  zapatillas+...               → 39 real URLs  (mín esperado 20)
  filtro+aceite+ford+focus     → 11 real URLs  (mín esperado 6)
  termotanque+rheem            → 40 real URLs  (mín esperado 20)
  harry+potter+tapa+dura       → 38 real URLs  (mín esperado 19)
  ```
  Usar estos como baseline inicial para `min_expected_real_urls`. Las 7 queries que faltan capturarse en la primera corrida del nightly y persistir su baseline.

- El sample 1/10 debe medir overhead empíricamente. Plan-task debe incluir un benchmark antes/después con la suite de tests integration: `pytest tests/integration/test_metrics_endpoint.py -k 'p99' -v` o similar.

- `Counter` para `parity_pla_units_missed` es probablemente lo correcto, pero validate que `inc()` no rompe la convención existente del proyecto.

- El cron `0 3 * * *` es UTC; en horario ART (UTC-3) es medianoche local. Si las pla-units bajan en horarios nocturnos (Google A/B testing al cambio de día), puede que sea peor para el baseline. Considerar `0 14 * * *` (medio día ART) como alternativa documentada — pero arrancar con 3am UTC y ajustar si ve problemas.
