## Implementation Decisions

### Traceability bookkeeping
- **D-01:** Flip `Status: Pending → Complete` en `.planning/REQUIREMENTS.md` para los 52 reqs que `02-VERIFICATION.md` confirma SATISFIED. OBS-07 ya está `Complete` — no tocar. **Por qué:** code-verified evidence existe; mantener `Pending` es bookkeeping stale que rompe el 3-source cross-reference del audit.
- **D-02:** Agregar `requirements_completed: [REQ-ID, REQ-ID, ...]` al frontmatter YAML de los 4 SUMMARYs faltantes (`02-01-SUMMARY.md`, `02-02-SUMMARY.md`, `02-03-SUMMARY.md`, `03-02-SUMMARY.md`). Mapear cada SUMMARY a sus reqs por subsystem: `02-01 → core-pipeline reqs`, `02-02 → llm+visit+fresh reqs`, `02-03 → deploy+obs+tests reqs`, `03-02 → resilience reqs`. **Por qué:** workflow Status Determination Matrix exige los 3 sources alineados.

### Test coverage
- **D-03:** En `tests/test_e2e.py:46` y `tests/test_e2e.py:87`, agregar header `X-API-Key` via `headers={"X-API-Key": os.getenv("E2E_API_KEY", "test-key-1")}` en las dos llamadas TestClient. **Por qué:** Phase 3 hizo auth mandatorio; sin header, e2e tests fallan 401 contra dev-box (incluso si CI verde por env-gate).
- **D-04:** Sibling test de degraded-mode usa **fixture SERP real** de `tests/fixtures/serp/*.html` (Phase 1, ej. `serp_pelota.html`). Monkeypatch `fetch_serp` para devolver el HTML, monkeypatch `router_health_check` → `False`, POST `/search` via TestClient, asertar `metadata.llm_degraded is True` AND `len(response.json()["results"]) > 0`. **Por qué:** D-18 (Phase 3) prohíbe `len > 0` shape checks vacíos, exige fixture-pinned realismo; audit pide explícitamente "realistic SERP HTML". Mirror del pattern S5 de `tests/integration/test_challenge_backoff.py:199`.

### Configuration drift (slowapi)
- **D-05:** **Single source-of-truth refactor** — derivar los decorator strings de `settings.API_RATE_PER_MINUTE` y `settings.API_RATE_PER_DAY` al module-load. Las opciones técnicas (lazy string, `slowapi.parse_many`, callable `key_func` extension, o module-level constants computed from settings antes del `@app.post`) las elige el researcher/planner. **Por qué:** la opción (b) "loguear los strings reales" hace visible el drift pero NO arregla la causa; bumpear env debería actualizar el hot path. Memoria `feedback_empirical_retest_after_default_changes` advierte exactamente esta clase de shadowing entre settings/contract/route.
- **D-06:** Verificación empírica post-fix — bumpar `API_RATE_PER_MINUTE` en `.env` (ej. 120), `compose build` + `compose up --force-recreate`, ejercitar `/search` 121 veces con la misma key y confirmar que la 121ª devuelve 429. **Por qué:** memoria `feedback_compose_build_recreate` + D-19 — el test unitario no detecta shadowing entre capas, solo el log del runtime con el valor real.

### Nyquist resolution
- **D-07:** Formal **accept uniforme** para Phase 1/2/3 VALIDATION.md. Cada uno actualiza frontmatter `status: draft → accepted`, `nyquist_compliant: true` (Phase 2 ya lo tiene), `wave_0_complete: true` con justificación inline en el body. **Por qué:** las 3 fases tienen VERIFICATION.md `status=passed` + integration WIRED + 53/53 reqs satisfied. Generar wave-0 tests retroactivos para algo ya empirically pasado es bookkeeping sin valor incremental.
- **D-08:** Justificaciones específicas por fase:
  - **Phase 1:** spike sin código de producción (entrega = SPIKE.md + fixtures). 0 v1 reqs. Wave-0 no aplica naturalmente.
  - **Phase 2:** 53 v1 reqs SATISFIED via `02-VERIFICATION.md`; `tests/test_parser.py::test_carousel_extracts_prices_from_fixtures` (D-18) actúa como wave-0 effectivo. `wave_0_complete: false` es draft sin actualizar.
  - **Phase 3:** OBS-07 + hardening overlay SATISFIED via `03-VERIFICATION.md` (6/6 success criteria + 21/21 threats + 10/10 UAT). Wave-0 tests existen como `tests/integration/test_*` — `wave_0_complete: false` también es draft sin actualizar.

### Phase 2 WARNINGs cleanup (oportunístico)
- **D-09:** Cerrar los 4 WR en una pasada:
  - **WR-01** (`src/artiscrapper/visit.py:330`): cambiar `"mercadolibre." in host` por suffix match contra el dominio efectivo (ej. `tldextract` o suffix check específico contra MELI variants). **Por qué:** evitar falsos positivos como `mercadoliberia.com`.
  - **WR-02** (`src/artiscrapper/main.py:457`): retener strong ref al `asyncio.create_task` de cache-write via `_BG_TASKS: set` module-level + `task.add_done_callback(_BG_TASKS.discard)`. **Por qué:** sin strong ref el GC puede colectar el task antes de completar (riesgo runtime documentado).
  - **WR-03** (`tests/test_footguns.py:62`): borrar la aserción tautológica o reemplazar por assert real que verifique el invariante intencionado.
  - **WR-04** (`tests/test_health.py:18-21`): reemplazar `NamedTemporaryFile` patrón leaky por fixture `tmp_path` de pytest. **Por qué:** evita archivos huérfanos en `/tmp` durante test runs.

### Claude's Discretion
- **Mecanismo exacto de wiring settings→decorator (D-05)** — slowapi soporta varias formas (limit string interpolada al import-time, `default_limits` desde settings, `limiter.limit(callable)`). El researcher pica la más limpia documentada en slowapi 0.1.9 docs; el patrón debe sobrevivir a `compose up --force-recreate` y mostrar el valor efectivo en `rate_limit_init` log.
- **Forma del `requirements_completed` YAML (D-02)** — flow style (`[REQ-01, REQ-02]`) vs block style (lista con guiones). Picar el que mantenga consistencia con el frontmatter existente del SUMMARY que se está editando.
- **Mapeo exacto REQ-ID → SUMMARY (D-02)** — usar `02-VERIFICATION.md` coverage tables como source-of-truth para asignar reqs a plans. El researcher cross-checkea con `key-files` de cada SUMMARY.
- **Fixture SERP específica para D-04** — `tests/fixtures/serp/serp_pelota.html` o cualquiera del set de 10 que el parser cascade procese sin error. El planner pica el que tenga ≥3 candidatos post-dedupe.
- **Si `tldextract` no está en pyproject (WR-01 fix)** — alternativa stdlib-only: comparar `host.split('.')[-3:]` o set comparison contra `{"mercadolibre.com.ar", "mercadolibre.com", "mercadolibre.cl", ...}`. Researcher decide.
- **Orden de los items en plans** — bookkeeping (D-01, D-02) primero porque son safe edits sin tocar runtime; tests (D-03, D-04) y refactor (D-05+D-06) después; WR (D-09) al final como cleanup batch.
